## 판정 규칙

> 여기는 왜 그렇게 정했는지를 적습니다. **식 자체는 [JUDGING.md](JUDGING.md)** 에
> 전부 있습니다 — 네 가지 판정 방식의 수식, 경계 조건, 실제 수치 예제.

### 비교 모집단은 시·도

시·군·구가 아닙니다. 시·군·구로 쪼개면 관내 주유소가 두세 곳뿐인 곳이 생겨
"관내 1위"가 아무 의미도 없어집니다. 시·도는 가장 작은 세종도 60곳이 넘습니다.

비교 지역은 명단 주소가 아니라 **오피넷이 말하는 현재 소재지**를 씁니다.
명단은 행정구역 개편을 못 따라갑니다 — 인천 서구는 검단구·서해구로 분구됐는데
명단은 아직 `서구`입니다.

### 신호등

```
🟢 가격기준 적합   그 시·도에서 상위 N위 이내
🟡 가격기준 근접   N위 밖이지만 2N위 이내
🔴 가격기준 초과   그보다 뒤
⚫ 과거 미신고     하루라도 가격을 거른 이력이 있음
⚪ 가격정보 없음   오늘 가격이 없어 판정 불가
```

`N` — **서울·경기 10위, 그 밖의 시·도 5위.** 서울(383곳)·경기(2,100여 곳)는
주유소가 압도적으로 많아 같은 5위 기준을 쓰면 사실상 아무도 통과하지 못합니다.
관리 화면에서 바꿀 수 있습니다.

### 순위는 조밀 순위

**1위가 세 곳 동점이면 다음은 4위가 아니라 2위입니다.** 같은 가격이면 같은
등수이고, 등수는 서로 다른 가격의 개수만큼만 존재합니다.

```
값     3,588  3,600  3,602  3,608  3,617 ×8  3,624 ×2  3,626
순위     1      2      3      4      5 ×8       6 ×2      7
```

커트라인도 같은 잣대입니다 — **N번째로 싼 가격**이지 배열의 N번째 값이
아닙니다. 동점이 많은 시·도일수록 커트라인이 뒤로 밀립니다.

### 계수 — 1이 합격선

그 시·도의 상위권 커트라인을 **1**로 두고 비례 환산합니다.

```
계수 ≤ 1   →  적합
계수  > 1   →  기준 초과
```

소수 **넷째 자리**까지 씁니다. 셋째 자리로는 1원 차이가 안 보입니다 — 합산
커트라인이 3,600원 언저리라 1원이 0.00028 이고, 3,608원과 3,609원이 둘 다
`1.002`로 찍혔습니다. 넷째 자리면 `1.0022` · `1.0025`로 갈립니다.

커트라인보다 1원 비싼 곳이 반올림으로 `1.0000`이 되지 않도록 막아 뒀습니다.
1은 합격선이라는 뜻이라 커트라인 이하일 때만 나와야 합니다.

### 기준 셋 — 통합 / 휘발유 / 경유

화면 우상단에서 전환합니다. 셋 모두 집계 단계에서 미리 계산해 싣습니다 —
화면에서 바꿀 때마다 전국 1만 건 분포를 다시 세울 수는 없습니다.

| 기준 | 값 | 모집단 |
|---|---|---|
| 통합 | 휘발유 + 경유 합계 | 두 유종을 **모두** 파는 주유소 |
| 휘발유 | 휘발유 가격만 | 휘발유를 파는 주유소 |
| 경유 | 경유 가격만 | 경유를 파는 주유소 |

모집단 크기가 기준마다 다릅니다(강원: 합산 600 / 휘발유 600 / 경유 602).
한 유종만 파는 곳이 있어서입니다.

**고급휘발유·실내등유는 다루지 않습니다.** 취급하지 않는 주유소가 대부분이라
판정이 '없음'으로 가득 차고, 제도의 관심 대상도 아닙니다.

## 화면

### 지도

전국 시·도 → 시·군·구 → 일반구 → **상세**, 네 단계로 내려갑니다.

- 지역마다 **이름 · 신호등 개수 · 비율 바**(빨·노·초 좌→우, 개수 비율만큼).
- 착한주유소가 없는 지역은 그리지 않고 상위 행정구역 외곽선만 옅게 남깁니다.
- 전국 보기만 기본 1.5배. 시·도로 들어가면 1배로 돌아옵니다 — 시·군·구 단계는
  투영이 이미 그 시·도에 맞춰져 있어 더 키우면 가장자리 군이 잘려 나갑니다.
- **상세 단계에서만** 실제 지도 타일 위에 주유기 아이콘 핀. 전국에 472개를
  찍으면 알아볼 수 없습니다.

배지 위치는 무게중심이 아니라 **최대내접원 중심**에서 잡습니다. 경기도는 서울을
둘러싸고 있어 무게중심이 서울 위에 얹힙니다. 핀 이름표는 아이콘 둘레의 후보
자리 중 다른 이름표와 모든 아이콘을 피하는 곳에 앉힙니다.

### 목록

- 열 머리를 눌러 정렬(오름 → 내림 → 해제). 값이 없는 행은 어느 방향이든 끝으로.
- 상호에 폴 코드가 붙습니다 — `대경주유소(HD)`.
- 휘발유·경유 가격 옆 괄호는 **그 유종만 놓고 본** 시·도 순위입니다.
- `기준 충족(일)` — 8월 1일부터 오늘까지 적합 / 근접 / 초과였던 날 수.
- 요약 띠의 여섯 칸을 누르면 그 판정만 걸러 봅니다.
- 상호 옆 **동그라미 숫자**가 선정차수입니다. 다섯 차수 넘게 뽑힌 곳에는
  `착하디착한` 이 붙습니다(22곳).
- **검색** — 이름·지역에 더해 조건을 섞어 씁니다. 띄어 쓰면 모두 만족하는 곳만
  남습니다: `9차`, `착하디착한`, `취소`, `계수<1`, `순위<=5`, `휘발유<1700`,
  `초과일>=100`, `적합`, `셀프`.
- **CSV 내려받기** — 보이는 순서 그대로, 세 기준의 순위·계수를 모두 담습니다.

### 판매가 추이

상호나 주유기 아이콘을 누르면 열립니다. 왼쪽에 그래프 **셋**, 오른쪽에 날짜별
기록표입니다. 기본 구간은 자료가 있는 처음(3월 1일)부터입니다.

| 그래프 | 무엇 |
|---|---|
| 판매가 | 휘발유·경유 (원/L) |
| 계수 | 1 이하가 상위권 |
| 단위지역 평균값 비교 | 이 주유소의 합계(파랑)와 그 시·도 평균(검정). 두 선 사이를 칠한 곳이 평균을 웃돈 구간 |

세 그래프는 x축이 정확히 포개지고 날짜 라벨은 맨 아래 칸에만 붙습니다. 옅은 띠와
점선은 **선정 기준기간과 그 마감일**입니다. 오른쪽 기록표의 `평균차` 열이 그날
시·도 평균과의 차이입니다.

그래프를 나눈 이유는 단위가 달라서입니다. 판매가는 1,700~2,000 대이고 계수는
0.94~1.15 라 한 그림에 이중축으로 얹으면 두 눈금을 번갈아 읽어야 합니다.
두 그래프는 같은 x 눈금을 써서 세로로 포개지므로 날짜 라벨은 아래에만 붙입니다.

- 기본 구간은 **8월 1일 ~ 최신일**이고 끝은 매일 밀립니다.
- 아직 안 받아온 구간에서는 선을 끊습니다. 직선으로 이으면 그동안 가격이
  그대로였던 것처럼 보입니다.
- 기록표는 최신 날짜가 위로. 값이 없는 날은 건너뛰지 않고 `정보없음`으로
  남깁니다 — 건너뛰면 신고를 거른 것인지 안 받아온 것인지 구분이 안 됩니다.

### 계수 검증 순위표

`CSV 내려받기` 옆 **`순위표 검증`** 버튼. 계수는 `그 값 ÷ 커트라인`인데
커트라인을 만든 전국 원본이 화면에 없어 확인할 길이 없었습니다.

날짜·시·도·기준을 고르면 그날 그 시·도를 줄 세운 결과가 나옵니다. 커트라인 줄에
색 선을 긋고 착한주유소를 강조해, 어디서 잘렸는지 눈으로 확인할 수 있습니다.

### 모바일

`720px` 아래에서만 다르게 그립니다. PC 화면은 손대지 않습니다.

지도와 목록은 본문에서 **보기만** 하고, 누르면 전체화면 시트가 열립니다.
지도는 손가락 끌기를 이동으로 먹어야 하고 페이지는 같은 동작으로 스크롤해야
하니, 한 화면에 같이 두면 둘 중 하나는 반드시 집니다.

목록은 카드로 바뀝니다 — 열 일곱 개짜리 표는 손바닥 화면에 들어가지 않습니다.

## 파이프라인

```
① normalize   stations.csv          → data/good-stations.json
② collect     오피넷 opDownload.do  → data/raw/{날짜}.json.gz
③ match       명단 ↔ 오피넷 코드    → data/station-mapping.json
④ aggregate   ②③ + 좌표 + 임계값    → client/public/data/latest.json
                                     → history.json · rank-{날짜}.json
⑤ push        판정 결과             → Supabase gs_daily (보관용)
```

`⓪ supabase:pull` 이 ① 앞에 붙어 명단·임계값·API 키를 내려받습니다.

**전부 GitHub Actions 가 돕니다.** Node 스크립트와 Playwright 만 쓰고 LLM 호출은
없습니다.

### 수집 주기

| 시각 (KST) | 잡히는 날짜 |
|---|---|
| 07:17 | 대개 전일분 |
| 11:17 | 대개 전일분 — 앞 자리가 날아갔을 때 받아내는 자리 |
| 16:47 | 당일분이 차 있으면 당일분 |
| 20:47 | 대개 당일분 |

**약속한 시각에 안 뜹니다.** GitHub 예약 실행은 대기열에 얹히는 best-effort 라
부하가 크면 밀리고, 밀린 채로 그냥 버려지기도 합니다. 실제로 잰 값입니다.

```
예정 01:20 UTC  →  09-04 05:59 UTC (+4h39m)
예정 01:20 UTC  →  09-05 05:51 UTC (+4h31m)
예정 10:30 UTC  →  09-05 13:29 UTC (+3h00m)
예정 01:20 UTC  →  09-06 아예 뜨지 않음      ← 이날 현황판이 멈췄다
```

하루 두 번으로는 한 번만 날아가도 그날이 통째로 비었습니다. 네 자리로 늘리고
분을 정시·30분에서 떼어 놨습니다 — 크론이 정각에 몰려서 그 언저리가 가장 많이
밀립니다. 워크플로 첫 단계가 예정 대비 지연을 로그에 찍고, 한 시간 넘게 밀리면
경고를 남깁니다.

급하면 기다리지 말고 손으로 돌리세요 — `gh workflow run collect.yml`.

`collect` 는 **어제~오늘을 기간 조회로 한 번에** 받아 그중 다 올라온 가장 최근
날짜를 씁니다. 오피넷은 당일분을 하루에 걸쳐 채우는데(9/5 17시에 이미 10,223건,
전날 10,237건), '어제'만 받으면 현황판이 늘 하루 뒤처집니다. 오늘 치가 전날
건수의 80%에 못 미치면 아직 올라오는 중으로 보고 물러섭니다.

### 명단은 오피넷 코드를 들고 온다

`stations.csv` 의 `번호` 열이 오피넷 주유소코드입니다. 상호·주소로 추정하던
매칭이 사실상 필요 없어져 **472/472 전건**이 확정됩니다.

시·도·시·군·구는 `지역` 열이 아니라 **주소**에서 뽑습니다. 지역 열은 시·군·구까지만
적혀 있어 일반구를 잃습니다 — 그것만 믿었더니 포항·천안·창원 등 8개 시의 56곳이
구 없이 남아, 지도에서 그 시로 내려가면 아무것도 안 뜨는 상태가 됐습니다.

### 원본은 보관한다

안 남겼더니 판정식을 바꿀 때마다 두 달치를 다시 긁느라 세 시간씩 썼습니다.

```
원본 3.5MB → gzip 317KB (8.7%) → 연 113MB
```

`data/raw/*.json.gz` 를 커밋합니다. 압축 안 한 `.json` 만 gitignore 로 막아
3.5MB 짜리가 실수로 들어가지 않게 합니다.

보관분을 읽어 다시 계산하는 것이 `backfill`(시계열) · `ranks`(순위표) ·
`reindex`(지역 정규화) 셋입니다. 오피넷을 다시 긁는 것은 `--redownload` 를
붙였을 때뿐입니다. **67일 전체 재계산이 3.4초**입니다.

## 처음 세팅

**Node 22** 가 필요합니다(CI 도 22 를 씁니다).

```bash
npm ci
npm run dev
```

데이터는 `client/public/data/` 에 커밋돼 있어 그대로 뜹니다. 수집 스크립트를
돌리려면 `npx playwright install chromium` 이 한 번 더 필요합니다.

### 키가 사는 곳

| 어디 | 무엇 | 없으면 |
|---|---|---|
| `client/public/config.js` | Supabase URL · **anon** 키 | 현황판은 정상, 관리 화면만 잠김 |
| `.env` (`.env.example` 복사) | `VITE_TILE_*` 배경 지도 타일 | OSM 공개 타일로 대체 |
| GitHub **Secrets** | `SUPABASE_SERVICE_ROLE_KEY` · `OPINET_API_KEY` · `VWORLD_API_KEY` · `VITE_TILE_URL` · `VITE_TILE_ATTRIBUTION` | 수집 잡이 Supabase 를 못 읽음 |
| GitHub **Variables** | `SUPABASE_URL` | 〃 |

> `config.js` 에는 **anon(publishable) 키만** 넣습니다. service_role / secret 키는
> 절대 넣지 마세요 — 이 파일은 공개 저장소에 그대로 올라갑니다.
> 오피넷·브이월드 키의 실제 값은 Supabase `gs_secret` 에 있고, 브라우저로는
> 이름과 설정 여부만 내려갑니다.

## 알아둘 것

**오피넷 기간 조회는 3일이 한계입니다.** 7일치는 10분을 기다려도 파일이
떨어지지 않습니다. 3일치(30,714행·4MB)는 정상입니다.

**브이월드 지오코더는 GitHub 러너에서 막힙니다.** 미국 IP 에서 호출하면 전건
실패합니다. 국내에서 한 번 채워 커밋하면 그 파일을 계속 씁니다.

**`supabase:pull` 이 명단을 덮어씁니다.** 저장소 명단만 바꾸고 Supabase 를
갱신하지 않으면 다음 수집에서 옛 명단으로 되돌아갑니다. 지금은 폴(상표) 정보
유무로 판별해 막고 있습니다.

**데이터 파일은 `cache: "no-cache"` 로 받습니다.** GitHub Pages 가
`max-age=600` 을 붙여, 배포 직후 10분간 새 코드가 옛 데이터를 읽는 구간이
생겼습니다. 파일 이름에 `?v=` 를 붙이는 것만으로는 부족했습니다 — 그 값이 번들
안에 박혀 있어 `index.html` 이 캐시돼 있으면 옛 값을 씁니다.

**광주와 전남은 따로 셉니다.** 행정구역상 둘은 전남광주통합특별시로 합쳐졌고
오피넷도 합쳐서 내려주지만, **선정은 여전히 둘을 따로 뽑습니다** — 명단 원본을
차수 × 시·도로 세어 보면 매 차수 광주 5곳, 전남 5곳이 따로 잡힙니다. 합쳐서
세면 1,030곳 한 모집단에 상위 5위 하나가 되어, 선정 때 열 자리였던 것이 다섯
자리로 줄어듭니다.

그래서 지도·드릴다운이 쓰는 시·도는 통합시 그대로 두고, **순위와 커트라인을
낼 때만** 옛 광주 다섯 자치구와 옛 전남 스물두 시·군으로 가릅니다
(`basisSido`). 이것만으로 전남광주 착한주유소의 적합이 5곳에서 8곳이 됐습니다.

**기준선은 마지막 선정차수를 씁니다.** 한 주유소가 여러 차수에 걸쳐 다시
뽑힙니다 — 172곳이 그렇고 다섯 번 뽑힌 곳도 있습니다. `stations.csv` 에는
최초 차수만 있어 명단 원본에서 따로 들여옵니다(`npm run rounds`).
마지막 차수로 세면 9차가 37곳이 아니라 93곳입니다.

**판정 방식이 둘입니다.** 명단 472곳은 아홉 차수에 걸쳐 뽑혔고 차수마다 선정
기준기간이 다릅니다. 그런데 순위 방식은 1차부터 9차까지 전부 '오늘의 상위 N위'
라는 한 잣대로 잽니다. 선정된 지 오래된 차수가 뒤로 밀리는 것은 그 주유소
사정이 아니라 잣대가 묻는 질문이 달라서입니다. 보관 원본으로 잰 값입니다.

```
차수   7월 기준 충족   8월 기준 충족   7월 시·도 백분위 중앙값
1차          3%             2%              상위 41%
3차          1%             3%              상위 33%
8차         80%            48%              상위 0.5%
9차          5%            59%              상위 2.5%
```

8차는 7월에, 9차는 8월에 몰립니다 — 차수가 곧 선정 기준기간입니다.

**보정** 은 대신 이렇게 묻습니다. 선정 시점에 견줘, 그 지역 시장이 오른 만큼을
빼고도 더 올렸는가.

```
기대가 E  = 기준가 P0 × (오늘 시장 M1 ÷ 기준기간 시장 M0)
이탈률    = (오늘 실제가 − E) ÷ E
```

시장 기준은 시·도 **중앙값** 입니다. 상위 N위 커트라인은 극단 순서통계량이라
싼 쪽 꼬리 몇 곳에 통째로 흔들리지만 중앙값은 꿈쩍하지 않습니다. 순위도 선정
때와 같은 잣대가 되도록, 선정 때 후보에서 빠졌던 것으로 보이는 주유소를 뺀
모집단에서 다시 셉니다(역산 49곳 + 제외요청 65곳, 겹침 5).

관리 화면에서 방식과 결합 조건을 고릅니다. 2026-09-08 자료로 적합이 이렇게
갈립니다 — 순위 91 · 보정(둘 다) 63. 선정 취소 대상 212곳은 어느 방식에서든
검정으로 먼저 빠집니다.

> 차수별 기준기간은 보관 원본(3월 1일~)에서 **추산**했습니다. 4~9차는 자기 기간
> 충족률이 73~84%로 확인됐고, 1~3차는 기간을 옳게 짚어도 5~13%에 그칩니다 —
> 그때는 가격 순위로 뽑은 것이 아니기 때문입니다. 근거와 수치는
> [ROUNDS.md §4](ROUNDS.md), 재현은 `npm run rounds:estimate` 입니다.
> 덮어쓰려면 `data/round-windows.json` 을 씁니다.

### 선정 취소 대상 — 검정

신호등 다섯 칸은 **오늘** 순위를 묻고, 검정은 다른 질문을 묻습니다.

> 뽑힌 뒤로 그 시·도 평균(휘발유+경유)보다 비싸게 판 날이 있는가.

최초 선정 공시일 다음날부터 매일 그 시·도 **평균**과 견줍니다. 계수의 분모는 상위
N위 커트라인이라 "평균보다 비쌌나"를 물을 수 없어, 시·도 일별 평균을 시계열에
따로 싣습니다. **한 번이라도 넘기면 대상**이고 지금 212곳입니다. 검정은 다른
무엇보다 앞서 색을 덮습니다 — 오늘 값을 믿을 수 있느냐 이전에 선정 자체를 다시
볼 일이기 때문입니다.

**값이 안 바뀐 날은 파일도 안 바뀝니다.** 집계 산출물에는 `generatedAt`,
수집 원본에는 `collectedAt` 이 박혀 있어, 예전에는 가격이 한 줄도 안 바뀐 날에도
파일 바이트가 달라졌습니다. 그래서 워크플로의 `변경 없음` 분기가 영영 잡히지
않고 실행할 때마다 데이터 커밋이 하나씩 쌓였습니다 — 9월 6일이 그랬습니다.
오피넷에 그날 치가 없어 전날 것을 그대로 다시 집었는데 커밋이 하나 올라갔고,
로그만 봐서는 진짜 갱신인지 알 수가 없었습니다.

지금은 시각 필드를 빼고 견줍니다. 같으면 옛 파일을 손대지 않으므로 옛 시각이
그대로 남습니다 — 그 시각은 '이 값이 만들어진 때' 이고, 값이 안 바뀌었으면
만들어진 때도 안 바뀐 것입니다. 화면의 `… 자동 수집 데이터 기준` 도 같은 뜻이라,
가격이 그대로면 시각도 움직이지 않습니다.

**Supabase 는 RLS 를 켜고 정책을 하나도 만들지 않았습니다.** anon 키로는
테이블을 읽지도 쓰지도 못하고, 모든 접근이 `SECURITY DEFINER` 함수를 거칩니다.
접근코드와 API 키가 브라우저로 내려오지 않습니다.

[HANDOVER.md](HANDOVER.md) 에 있습니다.
